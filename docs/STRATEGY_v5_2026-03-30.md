## 1. 문서 규칙

이 문서는 **현재 코드가 실제로 어떻게 동작하는지**만 기술한다.

표기 규칙:
- 기능 설명 뒤 **(구현 완료)** — 코드에서 런타임으로 동작함
- 기능 설명 뒤 **[부분구현]** — 유틸 함수는 존재하나 실행 경로에 연결되지 않음
- 상수 설명 뒤 **[상수만]** — `types.ts`에 정의되어 있으나 어떤 런타임 코드도 참조하지 않음
- 항목 뒤 **[미구현]** — 코드 없음

적용 범위 표기:
- **route** — `app/api/strategy/execute/route.ts` (수동 실행)
- **scheduler** — `lib/serverScheduler.ts` (자동 실행)
- **both** — 양쪽 모두

## 2. 전략 개요

6개 거래소(Binance, Bybit, OKX, Bitget, Gate, BingX)의 USDT 영구선물 펀딩레이트를 비교.
양수 스프레드가 비용을 초과하는 기회에 **숏(고FR) + 롱(저FR) 동시 진입 → 펀딩 수령 → 동시 청산** (Snipe).

## 3. 동작 모드: v1 (기본) vs v2 (opt-in)

`ConfirmedSnipeConfig`가 **`undefined`이거나 모든 토글이 `false`** 이면 아래 v1 동작이 적용된다.
**단, 거래소 프로파일 기반 진입 타이밍(3.1)은 토글과 무관하게 항상 적용된다.**

| 구분 | v1 동작 (토글 OFF / config 미설정) | v2 동작 (해당 토글 ON 시) |
|------|-----------------------------------|--------------------------|
| 진입 타이밍 | `max(profileLeadMs, legacyLeadMs)` **(항상 적용)** | 좌동 |
| 청산 | `targetFundingTime + closeDelayMs` | 펀딩 정산 확인 polling 후 청산 |
| 노셔널 | `investmentUSDT x leverage` 고정 | 오더북 depth cap 기반 동적 사이징 |
| 유동성 가드 (route) | `maxSlippagePercent` (1.5%) | round-trip impact 12bps hard cap |
| 유동성 가드 (scheduler) | `maxSlippagePercent` (1.5%) | **v1과 동일 — 미변경** |
| 주문 방식 | Post-Only → IOC → Market cascade | IOC-limit only |
| 헷지 pre-check | 없음 | ratio 0.998~1.002 |
| 헷지 트림 (route) | mismatch 2% | mismatch 0.20% |
| 거래소 등급 | Tier A/B/C 분류 **(항상 적용)** | 좌동 |

## 8. 구현 완료 기능 상세

### 8.1 Confirmed Close (scheduler)

**토글**: `useConfirmedClose`

활성화 조건: `true` + `pairSupportsConfirmedClose() === true` + `closeAttempts === 0`

1. 펀딩 시간에 close timer 발화 (`closeAt = targetFundingTime`, delay 없음)
2. `checkFundingSettled()` 2초 간격 polling
3. 양쪽 모두 `settled: true` → 즉시 동시 청산
4. `getPairMaxSettlementWaitMs()` 초과 → 강제 동시 청산 + 경고 로그
5. 조건 미충족 → v1 방식 (`targetFundingTime + closeDelayMs`) 유지

`checkFundingSettled()` (`lib/exchanges/index.ts`):
- `fetchFundingHistory(symbol, undefined, 5)`, 5초 타임아웃
- 예상 펀딩 시간 ±60초 이내 기록 매칭
- 실패 시 `{ settled: false }`

부수 효과: `useConfirmedClose: true`이면 scheduler poll 필터에서 **funding timestamp 정렬 3초 제한** 추가 적용.

### 8.2 IOC-Limit Only (both)

**토글**: `useIocLimitOnly`

`openPositionExact()`의 마지막 파라미터로 전달.

- `true`: Post-Only 시도 없이 IOC-limit 발사, 5초 타임아웃
- 체결률 < 90% → `OrderExecutionError` (partial execution 포함)
- 시장가 주문 발생하지 않음
- `false`: 기존 cascade (Post-Only → cancel → IOC → retry IOC)

### 8.3 Dynamic Notional (scheduler)

**토글**: `useDynamicNotional`

1. `fetchOrderbook()` 양쪽 (depth=50)
2. `calcOrderbookImpactBps()`로 각 side의 `depthCapNotional` 산출
3. `targetNotional = min(baseNotional, shortDepthCap, longDepthCap, dynamicNotionalCap)`
4. `targetNotional < $100` → `depth_insufficient`, 진입 skip (**floor 없음**)
5. orderbook fetch 실패 → `baseNotional` fallback + 경고 로그

**depth cap 계산**: 각 거래소 자체 mid `(bids[0]+asks[0])/2` 기준, per-side **6bps** 이내 수용 가능 금액.

> **impact 예산 관계**: depth cap(per-side 6bps)과 route.ts hard cap(round-trip 12bps)은 **독립 가드**다.
> - depth cap: "이 금액까지 한쪽 오더북이 6bps 이내로 소화 가능" → **사이징 힌트**
> - hard cap: "실제 체결 후 왕복 impact가 12bps 초과하면 거부" → **실행 방어선**
> - 양쪽 각 6bps면 entry 12bps, round-trip 24bps까지 이론상 가능 → depth cap 통과해도 hard cap에서 거부될 수 있음

### 8.4 Impact Guards (route만)

**토글**: `useImpactGuards`

```
roundTripImpactBps = (shortSlippage + longSlippage) x 2 x 100
→ maxRoundTripImpactBps (12) 초과 시 진입 거부
```

entry gap guard 연동:
- `true` → `entryGapThreshold = maxRoundTripImpactBps / 100` (%)
- `false` → `entryGapThreshold = maxSlippagePercent ?? 1.5` (%)

**scheduler는 미변경** — 여전히 `maxSlippagePercent` 기반. scheduler에 impact guard를 적용하려면 별도 작업 필요.

### 8.5 Strict Hedge (both, 부분 차이 있음)

**토글**: `useStrictHedge`

**진입 전 pre-check** (both):
```
hedgeRatio = |longNotionalEst / shortNotionalEst|
< 0.998 또는 > 1.002 → 진입 거부
```

**진입 후 트림** (route만):
- `true` → 트림 기준 0.20% (`MAX_HEDGE_MISMATCH_PCT`)
- `false` → 트림 기준 2% (legacy)

scheduler의 진입 후 트림은 v1 그대로 (route.ts처럼 0.20%로 바뀌지 않음).

## 9. 부분구현 기능 상세

### 9.1 Drift Buffer [부분구현]

**토글**: `useDriftBuffer` | **유틸**: `lib/opportunities.ts` | **실행 경로 연결**: 없음

```typescript
calcDriftBuffer(displayedRate, recentRateHistory?, exchangeUsesInstantRate?)
// history 없음: 일반 1bp, 즉시rate 거래소 max(1bp, |rate|x5%)
// history 있음: max(|last1mChange|, |last5mChange|x0.5, 1bp), 즉시rate x1.5
```

### 9.2 Conservative EV [부분구현]

**유틸**: `lib/opportunities.ts` | **실행 경로 연결**: 없음

```typescript
calcConservativeEV(notionalUSD, shortRate, longRate, shortDrift, longDrift,
                   roundTripFeePct, entryImpactPct, exitImpactPct)
// → { expectedNetUSD, passesMinProfit (>=$1.25), passesEVRatio (>=1.8), evRatio }
```

### 9.3 Time-Normalized Scoring [부분구현]

**유틸**: `lib/opportunities.ts` | **실행 경로 연결**: 없음

```typescript
calcTimeNormalizedScore(expectedNetUSD, capitalLockSec, fillProb?, fundingCaptureProb?)
// → expectedNetUSD x fillProb x fundingCaptureProb / capitalLockSec
```

**현재 진입 판단**: `calcNetSpreadPercent` / `calcHedgedNetSpreadPercent` (v1 방식).
위 세 유틸을 스케줄러 진입 경로에 연결하면 EV 기반 판단으로 전환됨.
