# Funding Fee Arbitrage Strategy v4

> 작성일: 2026-03-30
> 기준: 커밋 `145f384` (main)
> 상태: v2 토글 골격 구현 완료, 기본 OFF. Drift Buffer/Conservative EV는 부분구현. 담보 모니터링/상태머신/KPI 집계는 미구현.

---

## 1. 이 문서의 목적

**현재 코드가 실제로 어떻게 동작하는지**를 기록한다.

- 구현이 완료된 기능은 코드 위치와 동작을 기술한다.
- 유틸만 있고 런타임에 연결되지 않은 기능은 **[부분구현]** 으로 표기한다.
- 상수만 정의되어 있고 enforcement가 없는 항목은 **[상수만]** 으로 표기한다.
- 아직 코드가 없는 항목은 **[미구현]** 으로 표기한다.

---

## 2. 전략 개요

6개 거래소(Binance, Bybit, OKX, Bitget, Gate, BingX)의 USDT 영구선물 펀딩레이트를 비교.
양수 스프레드가 비용을 초과하는 기회에 **숏(고FR) + 롱(저FR) 동시 진입 → 펀딩 수령 → 동시 청산** (Snipe).

### v1 → v2 변경 대비

| 항목 | v1 (기존, 기본 동작) | v2 (opt-in, 토글 ON 시) | 구현 상태 |
|------|---------------------|------------------------|-----------|
| 진입 타이밍 | 고정 `entryLeadMs` (3.5s) | 거래소 프로파일 기반 (5~35s) | 구현 완료 |
| 청산 | 고정 `closeDelayMs` (1s) | 펀딩 정산 확인 polling 후 청산 | 구현 완료 |
| 노셔널 | `investmentUSDT x leverage` 고정 | 오더북 depth cap 기반 동적 사이징 | 구현 완료 |
| 유동성 가드 (route.ts) | `maxSlippagePercent` (1.5%) | round-trip impact bps hard cap | 구현 완료 |
| 유동성 가드 (scheduler) | `maxSlippagePercent` (1.5%) | **v1과 동일 (legacy 유지)** | 미변경 |
| 주문 방식 | Post-Only → IOC → Market | IOC-limit only (시장가 금지) | 구현 완료 |
| 헷지 기준 | mismatch 2% 트림 | ratio pre-check + 0.20% 트림 | 구현 완료 |
| 거래소 등급 | 동등 취급 | Tier A/B/C + capability flags | 구현 완료 |
| Drift buffer | 없음 | 표시 funding 보수적 보정 | **부분구현** |
| Conservative EV | 없음 | EV 기반 진입 판단 | **부분구현** |
| 담보/청산 모니터링 | 없음 | free collateral, liquidation buffer | **미구현** |
| 상태 머신 | 없음 | 12단계 실행 상태 | **미구현** |

**핵심 원칙**: `ConfirmedSnipeConfig` 미설정 = v1 동작 100% 유지. 각 기능은 독립 토글.

**Tier 의미**:

- `supportsFundingSettlementCheck` — confirmed close 사용 가능 여부

**헬퍼 함수**:
- `getPairEntryLeadMs(short, long)` — 두 거래소 중 더 긴 entry lead (ms)
- `getPairMaxSettlementWaitMs(short, long)` — 더 긴 settlement wait (ms)
- `hasTierCExchange(short, long)` — Tier C 포함 여부
- `pairSupportsConfirmedClose(short, long)` — 양쪽 모두 settlement check 가능
- `pairSupportsIocLimit(short, long)` — 양쪽 모두 IOC 지원

## 6. 기능 상세 — 구현 완료

### 6.1 Confirmed Close

**토글**: `useConfirmedClose` | **적용 범위**: `serverScheduler.ts`

1. `useConfirmedClose: true` + `pairSupportsConfirmedClose() === true` + `closeAttempts === 0`일 때 활성화
2. 펀딩 시간에 close timer 발화 (`closeAt = targetFundingTime`, delay 없음)
3. `checkFundingSettled()` 2초 간격 polling
4. 양쪽 모두 `settled: true` → 즉시 동시 청산
5. `getPairMaxSettlementWaitMs()` 초과 → 강제 동시 청산 + 경고 로그
6. 조건 미충족 시 v1 방식 (`targetFundingTime + closeDelayMs`) 유지

`checkFundingSettled()` (`lib/exchanges/index.ts`):
- `fetchFundingHistory(symbol, undefined, 5)` 호출, 5초 타임아웃
- 예상 펀딩 시간 ±60초 이내 기록 매칭
- 실패 시 `{ settled: false }` 반환

### 6.2 IOC-Limit Only

**토글**: `useIocLimitOnly` | **적용 범위**: `exchanges/index.ts`, `serverScheduler.ts`, `route.ts`

- `true`: Post-Only 시도 없이 IOC-limit 한 번 발사, 5초 타임아웃
- 체결률 < 90% → `OrderExecutionError` (partial execution 정보 포함)
- 시장가 주문 발생하지 않음
- `false`(기본): 기존 cascade 유지 (Post-Only → cancel → IOC → retry IOC)

### 6.3 Dynamic Notional

**토글**: `useDynamicNotional` | **적용 범위**: `serverScheduler.ts`

1. `fetchOrderbook()` 양쪽 호출 (depth=50)
2. `calcOrderbookImpactBps()`로 각 side의 `depthCapNotional` 산출
3. `targetNotional = min(baseNotional, shortDepthCap, longDepthCap, dynamicNotionalCap)`
4. `targetNotional < $100` → `depth_insufficient` 기록, 진입 skip (**floor 없음**)
5. orderbook fetch 실패 → `baseNotional`로 fallback + 경고 로그

**`depthCapNotional` 계산** (`lib/exchanges/index.ts`):
- 각 거래소 자체 mid price `(bids[0] + asks[0]) / 2` 기준
- 오더북 레벨 순회하면서 **per-side 6bps** 이내 수용 가능한 최대 금액
- 코드: `const perSideCapBps = 6;`

> **impact 예산 관계 정리**:
> - `depthCapNotional`은 **per-side 6bps** 기준. 양쪽 6+6=12bps entry, round-trip 24bps까지 허용하는 셈.
> - `route.ts`의 `maxRoundTripImpactBps = 12`는 별도 가드로, **실제 체결 후** 왕복 impact를 검사.
> - 두 기준은 **독립적으로 작동**한다. depth cap을 통과해도 hard cap에서 거부될 수 있다.
> - depth cap은 "이 금액까지 한쪽 오더북이 6bps 이내로 소화 가능"이라는 **사이징 힌트**이고, hard cap은 **실행 시점 최종 방어선**이다.

### 6.4 Impact Guards

**토글**: `useImpactGuards` | **적용 범위**: `route.ts`만 (scheduler는 legacy slippage 유지)

route.ts 구현:
```
roundTripImpactBps = (shortSlippage + longSlippage) x 2 x 100
→ maxRoundTripImpactBps (기본 12) 초과 시 진입 거부
```

entry gap guard 연동:
```
useImpactGuards: true  → entryGapThreshold = maxRoundTripImpactBps / 100 (%)
useImpactGuards: false → entryGapThreshold = maxSlippagePercent ?? 1.5 (%)
```

**serverScheduler.ts는 변경 없음** — 여전히 `maxSlippagePercent` 기반 가드 사용.
→ 향후 scheduler에도 impact guard를 적용하려면 별도 작업 필요.

### 6.5 Strict Hedge

**토글**: `useStrictHedge` | **적용 범위**: `serverScheduler.ts` + `route.ts`

진입 전:
```
hedgeRatio = |longNotionalEst / shortNotionalEst|
hedgeRatio < 0.998 또는 > 1.002 → 진입 거부
```

진입 후 (route.ts):
```
useStrictHedge: true  → 트림 기준 0.20%
useStrictHedge: false → 트림 기준 2% (기존)
```

### 6.6 진입 타이밍 (프로파일 기반)

**항상 적용** (토글 없음) | **적용 범위**: `serverScheduler.ts`

```typescript
entryLeadMs = max(getPairEntryLeadMs(short, long), legacyTimingConfig.entryLeadMs)
```

| 페어 | profileLeadMs | 최종 적용 |
|------|---------------|-----------|
| Binance ↔ Bybit | 7000 | 7000 |
| Bybit ↔ Gate | 5000 | 5000 |
| OKX ↔ 아무거나 | 7000 | 7000 |
| BingX ↔ 아무거나 | 35000 | 35000 |

Tier C 필터: `hasTierCExchange() === true`이면 해당 거래소가 `enabledExchanges`에 명시적으로 포함될 때만 허용.

### 6.7 Funding Timestamp 정렬

**조건**: `useConfirmedClose: true` | **적용 범위**: `serverScheduler.ts` poll 필터

```
|shortFundingTime - longFundingTime| > 3초 → 기회 제외
```

discovery 단계의 120초 tolerance는 유지 (UI 목록 표시용).

## 7. 기능 상세 — 부분구현

### 7.1 Drift Buffer

**토글**: `useDriftBuffer` | **유틸 구현**: `lib/opportunities.ts` | **스케줄러 연결**: 없음

구현된 함수:
```typescript
calcDriftBuffer(displayedRate, recentRateHistory?, exchangeUsesInstantRate?)
// history 없음: 일반 1bp, 즉시rate 거래소 max(1bp, |rate|x5%)
// history 있음: max(|last1mChange|, |last5mChange|x0.5, 1bp), 즉시rate x1.5
```

### 7.2 Conservative EV

**유틸 구현**: `lib/opportunities.ts` | **스케줄러 연결**: 없음

```typescript
calcConservativeEV(notionalUSD, shortRate, longRate, shortDrift, longDrift,
                   roundTripFeePct, entryImpactPct, exitImpactPct)
// → { expectedNetUSD, passesMinProfit (>=$1.25), passesEVRatio (>=1.8), evRatio }
```

### 7.3 Time-Normalized Scoring

**유틸 구현**: `lib/opportunities.ts` | **스케줄러 연결**: 없음

```typescript
calcTimeNormalizedScore(expectedNetUSD, capitalLockSec, fillProb?, fundingCaptureProb?)
// → score = expectedNetUSD x fillProb x fundingCaptureProb / capitalLockSec
```

**현재 진입 판단**: 기존 `calcNetSpreadPercent` / `calcHedgedNetSpreadPercent` 기반.
**향후**: 위 세 유틸을 스케줄러 진입 경로에 연결하면 EV 기반 판단으로 전환됨.

## 9. 리스크 관리

### 9.1 진입 가드 체인

**실행 순서** (route.ts 수동 실행 기준):

| 순서 | 가드 | 조건 | v2 변경 | 적용 범위 |
|------|------|------|---------|-----------|
| 1 | Balance check | 잔고 >= margin + fee | 변경 없음 | route + scheduler |
| 2a | Impact guard | `roundTripImpactBps > 12` | **v2 신규** | route.ts만 |
| 2a' | Slippage guard | `slippage > maxSlippage%` | v1 유지 | scheduler + route(OFF시) |
| 2b | Entry gap | `\|entryGapPct\| > threshold` | threshold 소스 변경 | route.ts만 |
| 2c | Profitability | `realNetSpread <= 0` | 변경 없음 | route + scheduler |
| 3 | Hedge ratio | `ratio < 0.998 or > 1.002` | **v2 신규** | route + scheduler |
| 4 | Depth check | `targetNotional < $100` | **v2 신규** | scheduler만 |
| 5 | Timestamp | `\|shortFT - longFT\| > 3s` | **v2 신규** | scheduler만 |

### 9.2 진입 후 가드

| 가드 | 조건 | 동작 | 적용 범위 |
|------|------|------|-----------|
| Hedge trim | `diffPercent > 0.20%` (strict) 또는 `> 2%` (legacy) | 초과분 부분 청산 | route.ts |
| One-leg failure | 한쪽 실패 | 성공 측 + partial 전부 rollback | route + scheduler |
| Close retry | 청산 실패 | 30초 후 재시도, 성공 leg 기록 | scheduler |

### 9.3 [미구현] 향후 추가

- `freeCollateralRatio` 실시간 모니터링 + 신규 진입 금지
- `distanceToLiquidation` 기반 flatten
- Kill-Switch 자동화 (현재는 `stats.errors` 카운팅 + 텔레그램 알림)
- 정식 상태 머신 (`idle → discover → ... → cooldown`)

| Orphan leg 시간 제한 | 상수만 | `MAX_ORPHAN_LEG_MS = 300` 런타임 enforcement |
| 정식 상태 머신 | 미구현 | `idle → discover → ... → cooldown` |
| 승격 KPI 자동 집계 | 미구현 | `fundingCaptureRate`, `forcedCloseRate` 등 |
