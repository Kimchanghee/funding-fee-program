## 1. 이 문서의 목적

이 문서는 **현재 코드에 구현된 최종 상태**를 정확히 기술한다.
"이렇게 하면 좋겠다"가 아니라 "코드가 실제로 이렇게 동작한다"를 기록한다.

코드에 아직 구현되지 않은 항목(live account fee 조회, `requiresLiveFundingMeta` 플래그, `freeCollateralRatio` 실시간 모니터링 등)은 **[미구현]** 으로 표기하고, 향후 구현 방향만 간략히 언급한다.

## 2. 전체 구조 요약

### 2.1 전략

6개 거래소(Binance, Bybit, OKX, Bitget, Gate, BingX)의 USDT 영구선물 펀딩레이트를 비교해,
양수 스프레드가 비용을 초과하는 기회에 **숏(고FR) + 롱(저FR) 동시 진입 → 펀딩 수령 → 동시 청산**하는 Snipe 전략.

### 2.2 v1 → v2 변경 대비

| 항목 | v1 (기존, 기본 동작) | v2 (opt-in, 토글 ON 시) |
|------|---------------------|------------------------|
| 진입 타이밍 | 고정 `entryLeadMs` (기본 3.5s) | 거래소 프로파일 기반 (5~35s) |
| 청산 | 고정 `closeDelayMs` (기본 1s) | 펀딩 정산 확인 polling 후 청산 |
| 노셔널 | `investmentUSDT x leverage` 고정 | 오더북 depth cap 기반 동적 사이징 |
| 유동성 가드 | `maxSlippagePercent` (기본 1.5%) | round-trip impact bps hard cap |
| 주문 방식 | Post-Only → IOC → Market cascade | IOC-limit only (시장가 금지) |
| 헷지 기준 | mismatch 2% 트림 | ratio 0.998~1.002 pre-check + 0.20% 트림 |
| 거래소 등급 | 동등 취급 | Tier A/B/C + capability flags |

**핵심 원칙**: `ConfirmedSnipeConfig` 미설정 = v1 동작 100% 유지. 각 기능은 독립 토글.

## 6. 각 기능 상세 — 구현된 동작

### 6.1 Confirmed Close

**토글**: `useConfirmedClose`

**동작** (`lib/serverScheduler.ts` — `executeClose`):

1. `useConfirmedClose: true` + `pairSupportsConfirmedClose() === true` + `closeAttempts === 0`일 때 활성화
2. 펀딩 시간에 close timer 발화 (`closeAt = targetFundingTime`, delay 없음)
3. `checkFundingSettled()` 2초 간격 polling 시작
4. 양쪽 모두 `settled: true` → 즉시 동시 청산
5. `getPairMaxSettlementWaitMs()` 초과 → 강제 동시 청산 + 경고 로그
6. 조건 미충족 시 v1 방식 (`targetFundingTime + closeDelayMs`) 그대로 사용

**`checkFundingSettled()` 구현** (`lib/exchanges/index.ts`):
- `fetchFundingHistory(symbol, undefined, 5)` 호출
- 예상 펀딩 시간 +/- 60초 이내 기록 매칭
- 5초 타임아웃, 실패 시 `{ settled: false }`

### 6.2 IOC-Limit Only

**토글**: `useIocLimitOnly`

**동작** (`lib/exchanges/index.ts` — `openPositionExact`):

1. `useIocLimitOnly: true`이면 Post-Only 시도 없이 바로 IOC-limit 발사
2. `timeInForce: 'IOC'`, 5초 타임아웃
3. 체결률 < 90% → `OrderExecutionError` (partial execution 정보 포함)
4. 시장가 주문 발생하지 않음

`false`(기본)이면 기존 cascade 유지: Post-Only → cancel → IOC → retry IOC

**전달 경로**: `serverScheduler.executeEntry()` + `route.ts POST` 모두 `openPositionExact(..., snipeConfig.useIocLimitOnly)` 로 전달

### 6.3 Dynamic Notional

**토글**: `useDynamicNotional`

**동작** (`lib/serverScheduler.ts` — `executeEntry`):

1. `fetchOrderbook()` 양쪽 호출 (depth=50)
2. `calcOrderbookImpactBps()` 로 각 side의 `depthCapNotional` 산출
3. `targetNotional = min(baseNotional, shortDepthCap, longDepthCap, dynamicNotionalCap)`
4. `targetNotional < $100` → `depth_insufficient` 기록, 진입 skip (floor 없음)
5. orderbook fetch 실패 → `baseNotional`로 fallback + 경고 로그

**`depthCapNotional` 계산** (`lib/exchanges/index.ts` — `calcOrderbookImpactBps`):
- 각 거래소 자체 mid price `(bids[0] + asks[0]) / 2` 기준
- 오더북 레벨 순회하면서 **per-side 6bps** 이내 수용 가능한 최대 금액
- 코드: `const perSideCapBps = 6;`

### 6.4 Impact Guards

**토글**: `useImpactGuards`

**동작** (`app/api/strategy/execute/route.ts` + `lib/serverScheduler.ts`):

route.ts 구현:
```
roundTripImpactBps = (shortSlippage + longSlippage) x 2 x 100
→ maxRoundTripImpactBps (기본 12) 초과 시 진입 거부
```

entry gap guard 연동:
```
useImpactGuards: true  → entryGapThreshold = maxRoundTripImpactBps / 100 (%)
useImpactGuards: false → entryGapThreshold = maxSlippagePercent ?? 1.5 (%)
```

serverScheduler.ts:
- 기존 `maxSlippagePercent` 기반 가드가 그대로 적용됨
- impact guard는 route.ts에서만 구현 (스케줄러는 기존 slippage 가드 유지)

### 6.5 Strict Hedge

**토글**: `useStrictHedge`

**동작**:

진입 전 (`serverScheduler.ts` + `route.ts`):
```
hedgeRatio = |longNotionalEst / shortNotionalEst|
hedgeRatio < 0.998 또는 > 1.002 → 진입 거부 (hedge_ratio_exceeded)
```

진입 후 (`route.ts`):
```
useStrictHedge: true  → 트림 기준 0.20%
useStrictHedge: false → 트림 기준 2% (기존)
```

### 6.6 Drift Buffer

**토글**: `useDriftBuffer`

**현재 상태**: 유틸리티 함수 구현 완료, 스케줄러 자동 적용은 **미연결**

구현된 함수 (`lib/opportunities.ts`):

```typescript
calcDriftBuffer(displayedRate, recentRateHistory?, exchangeUsesInstantRate?)
// history 없음: 일반 1bp, 즉시rate 거래소 max(1bp, |rate|x5%)
// history 있음: max(|last1mChange|, |last5mChange|x0.5, 1bp), 즉시rate x1.5

calcConservativeEV(notionalUSD, shortRate, longRate, shortDrift, longDrift,
                   roundTripFeePct, entryImpactPct, exitImpactPct)
// → { expectedNetUSD, passesMinProfit, passesEVRatio, evRatio, ... }

calcTimeNormalizedScore(expectedNetUSD, capitalLockSec, fillProb?, fundingCaptureProb?)
// → score = expectedNetUSD x fillProb x fundingCaptureProb / capitalLockSec
```

**[미구현]**: 스케줄러에서 `calcDriftBuffer`를 자동으로 호출해 EV 기반 진입 판단을 하는 로직은 아직 연결되지 않음. 현재는 기존 `calcNetSpreadPercent` / `calcHedgedNetSpreadPercent` 기반 판단.

## 7. 진입 타이밍

### 7.1 구현 (`lib/serverScheduler.ts` — `scheduleEntry`)

```typescript
const profileLeadMs = getPairEntryLeadMs(shortExchange, longExchange);
const legacyLeadMs = this.getTimingConfig().entryLeadMs;  // 기본 3500ms
const entryLeadMs = Math.max(profileLeadMs, legacyLeadMs);
```

| 페어 예시 | profileLeadMs | 최종 적용 |
|-----------|---------------|-----------|
| Binance <-> Bybit | 7000 | 7000 |
| Bybit <-> Gate | 5000 | 5000 (legacy 3500보다 큼) |
| OKX <-> 아무거나 | 7000 | 7000 |
| BingX <-> 아무거나 | 35000 | 35000 |

### 7.2 Tier C 필터

`hasTierCExchange() === true`이면, 해당 Tier C 거래소가 `enabledExchanges`에 명시적으로 포함되어 있을 때만 스케줄링 허용.

### 7.3 Funding Timestamp 정렬

`useConfirmedClose: true`일 때, poll 필터에서:
```
rates에서 short/long의 nextFundingTime 차이 > 3초 → 기회 제외
```

discovery 단계의 120초 tolerance는 유지 (UI 목록 표시용).

## 8. 수수료 체계

### 8.1 현재 구현

`lib/types.ts` — `EXCHANGE_FEES` (Referral Max 프리셋):

| 거래소 | Taker | Maker |
|--------|-------|-------|
| Binance | 0.040% | 0.016% |
| Bybit | 0.044% | 0.016% |
| OKX | 0.040% | 0.016% |
| Bitget | 0.048% | 0.016% |
| Gate | 0.040% | 0.016% |
| BingX | 0.040% | 0.016% |

우선순위: `feeOverrides[exchange] ?? EXCHANGE_FEES[exchange]`

### 8.2 IOC-limit only 시 수수료

`useIocLimitOnly: true`이면 항상 taker fee 기준으로 비용 산출.
기존 cascade에서는 maker/taker/mixed로 구분.

### 8.3 [미구현] 향후 개선

- `liveAccountFee` 실시간 조회 (API 기반)
- 레퍼럴/리베이트를 Decision EV에서 제외하고 `realizedRebateUSD`로만 사후 집계
- 현재는 프리셋 + feeOverrides 방식으로 운영

## 9. 리스크 관리 — 구현된 가드

### 9.1 진입 가드 체인 (route.ts + serverScheduler.ts)

| 순서 | 가드 | 조건 | v2 변경 |
|------|------|------|---------|
| 1 | Balance check | 양쪽 잔고 >= margin + entry fee | 변경 없음 |
| 2a | Impact guard | `roundTripImpactBps > maxRoundTripImpactBps` | **v2 신규** (useImpactGuards) |
| 2a' | Slippage guard | `slippage > maxSlippagePercent` | v1 유지 (useImpactGuards: false) |
| 2b | Entry gap | `|entryGapPct| > threshold` | threshold 소스 변경 |
| 2c | Profitability | `realNetSpread <= 0` | 변경 없음 |
| 3 | Hedge ratio | `ratio < 0.998 or > 1.002` | **v2 신규** (useStrictHedge) |
| 4 | Depth check | `targetNotional < $100` | **v2 신규** (useDynamicNotional) |
| 5 | Timestamp | `|shortFT - longFT| > 3s` | **v2 신규** (useConfirmedClose) |

### 9.2 진입 후 가드

| 가드 | 조건 | 동작 |
|------|------|------|
| Hedge trim | `diffPercent > 0.20%` (strict) 또는 `> 2%` (legacy) | 초과분 부분 청산 |
| One-leg failure | 한쪽 실패 | 성공 측 + partial 전부 rollback |
| Close retry | 청산 실패 | 30초 후 재시도, 성공 leg 기록 |

### 9.3 [미구현] 향후 추가

- `freeCollateralRatio` 실시간 모니터링 + 신규 진입 금지
- `distanceToLiquidation` 기반 flatten
- Kill-Switch 자동화 (현재는 `stats.errors` 카운팅 + 텔레그램 알림)
- 정식 상태 머신 (`idle → discover → ... → cooldown`)
