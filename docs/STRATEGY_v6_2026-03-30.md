## 1. 문서 규칙

이 문서는 **현재 코드가 실제로 어떻게 동작하는지**만 기록한다.
권장 설계나 향후 개선안이 아니라, **지금 코드 기준의 런타임 동작**을 정리한 문서다.

### 표기 규칙

- **(구현 완료)**: 코드에서 실제 런타임으로 동작함
- **[부분구현]**: 유틸 함수 또는 일부 연결만 존재하고, 실행 경로 전체에는 완전히 연결되지 않음
- **[상수만]**: `types.ts` 등에 상수는 정의되어 있으나 런타임에서 참조되지 않음
- **[미구현]**: 해당 기능의 코드가 없음

### 적용 범위 표기

- **route**: `app/api/strategy/execute/route.ts` (수동 실행 경로)
- **scheduler**: `lib/serverScheduler.ts` (자동 실행 경로)
- **both**: route + scheduler 모두

## 2. 전략 개요

6개 거래소(Binance, Bybit, OKX, Bitget, Gate, BingX)의 USDT 영구선물 펀딩레이트를 비교한다.
양수 스프레드가 비용을 초과하는 기회에서 **숏(고 funding) + 롱(저 funding)** 으로 동시에 진입하고,
펀딩 수령 후 양쪽 포지션을 청산하는 **Funding Fee Snipe 전략**이다.

## 3. 동작 모드: 기본(v1 계열) vs 토글 활성(v2 계열)

`ConfirmedSnipeConfig`가 `undefined`이거나 모든 토글이 `false`이면,
**주문·청산·사이징의 기본 흐름은 v1 계열 동작**을 따른다.

다만 아래 두 항목은 토글과 무관하게 **항상 적용**된다.

- 거래소 프로파일 기반 진입 타이밍 (4.1)
- Tier C 거래소 필터 (4.2)

즉, **토글 OFF = 완전한 과거 v1 100% 재현**은 아니며,
기본 흐름은 v1 계열이지만 일부 공통 로직은 이미 반영된 상태다.

| 구분 | 기본 동작 (토글 OFF / config 미설정) | 토글 ON 시 확장 동작 |
|------|-------------------------------------|----------------------|
| 진입 타이밍 | `max(profileLeadMs, legacyLeadMs)` **항상 적용** | 동일 |
| 청산 | `targetFundingTime + closeDelayMs` | `useConfirmedClose` ON 시 settlement polling 후 청산 |
| 노셔널 | `investmentUSDT x leverage` 고정 | `useDynamicNotional` ON 시 depth cap 기반 동적 사이징 |
| 유동성 가드 (route) | `maxSlippagePercent` (기본 1.5%) | `useImpactGuards` ON 시 round-trip impact hard cap |
| 유동성 가드 (scheduler) | `maxSlippagePercent` (기본 1.5%) | **현재 동일 — impact guard 미적용** |
| 주문 방식 | Post-Only → cancel → IOC → retry IOC | `useIocLimitOnly` ON 시 IOC-limit only |
| 헷지 pre-check | 없음 | `useStrictHedge` ON 시 ratio 0.998~1.002 검사 |
| 헷지 트림 (route) | mismatch 2% | `useStrictHedge` ON 시 mismatch 0.20% |
| 거래소 등급 | Tier A/B/C 분류 **항상 적용** | 동일 |
| Drift Buffer | 미사용 | `useDriftBuffer` 토글 존재하나 현재 실행 경로 미연결 |

## 8. 구현 완료 기능 상세

### 8.1 Confirmed Close (구현 완료, scheduler)

**토글**: `useConfirmedClose`

활성화 조건:

- `useConfirmedClose === true`
- `pairSupportsConfirmedClose(short, long) === true`
- `closeAttempts === 0`

동작 순서:

1. close timer를 `targetFundingTime`에 맞춰 발화
2. `checkFundingSettled()`를 2초 간격으로 polling
3. 양쪽 모두 `settled: true`이면 즉시 동시 청산
4. `getPairMaxSettlementWaitMs()`를 초과하면 강제 청산 + 경고 로그
5. 조건이 맞지 않으면 v1 계열 방식(`targetFundingTime + closeDelayMs`) 사용

`checkFundingSettled()` 구현 (`lib/exchanges/index.ts`):

- `fetchFundingHistory(symbol, undefined, 5)` 호출
- 예상 funding 시간 ±60초 이내 기록 탐색
- 5초 타임아웃
- 실패 시 `{ settled: false }` 반환

추가 효과:

- `useConfirmedClose`가 켜져 있으면 scheduler poll 단계에서 funding timestamp 정렬 3초 제한이 같이 적용된다.

### 8.2 IOC-Limit Only (구현 완료, both)

**토글**: `useIocLimitOnly`

`openPositionExact()`의 마지막 파라미터로 전달된다.

- `true`: Post-Only 시도 없이 IOC-limit 한 번 발사
- 타임아웃: 5초
- 체결률 `< 90%`: `OrderExecutionError`
- 시장가 주문은 발생하지 않음
- `false`: 기존 cascade 유지 (Post-Only → cancel → IOC → retry IOC)

### 8.3 Dynamic Notional (구현 완료, scheduler)

**토글**: `useDynamicNotional`

동작 순서:

1. 양쪽 오더북을 `fetchOrderbook(depth=50)`로 조회
2. `calcOrderbookImpactBps()`로 각 side의 `depthCapNotional` 산출
3. 아래 식으로 최종 노셔널 결정

```text
targetNotional = min(baseNotional, shortDepthCap, longDepthCap, dynamicNotionalCap)
```

4. `targetNotional < $100`이면 `depth_insufficient`로 기록하고 진입 skip
5. 오더북 조회 실패 시 `baseNotional` fallback + 경고 로그

`depthCapNotional` 계산 기준:

- 각 거래소의 자체 mid price `(bestBid + bestAsk) / 2`
- 오더북 레벨을 순회하면서 **per-side 6bps** 이내에서 수용 가능한 최대 금액 계산
- 코드 상수: `const perSideCapBps = 6`

> **주의**  
> 현재 코드에서 `depthCapNotional`의 per-side 6bps 기준과, route의 `maxRoundTripImpactBps = 12`는 **서로 독립적인 가드**다.  
> 즉, depth cap은 사이징 힌트이고, route hard cap은 실제 실행 시점의 최종 차단선이다.  
> 둘은 완전히 단일 budget 모델로 통합되어 있지 않다.

### 8.4 Impact Guards (구현 완료, route만)

**토글**: `useImpactGuards`

현재는 **수동 실행 route에서만** 적용된다.
`scheduler`는 아직 기존 `maxSlippagePercent` 기반 가드를 사용한다.

계산식:

```text
roundTripImpactBps = (shortSlippage + longSlippage) × 2 × 100
```

> 여기서 `shortSlippage`, `longSlippage`는 **% 단위 값**이며, `×100`을 통해 bps로 변환한다.

판정:

```text
roundTripImpactBps > maxRoundTripImpactBps (기본 12) → 진입 거부
```

entry gap threshold 연동:

- `useImpactGuards = true` → `entryGapThreshold = maxRoundTripImpactBps / 100`
- `useImpactGuards = false` → `entryGapThreshold = maxSlippagePercent ?? 1.5`

즉, route에서는 impact 기반 가드로 전환되지만,
scheduler는 아직 legacy slippage guard를 그대로 사용한다.

### 8.5 Strict Hedge (구현 완료, both / 일부 차이 있음)

**토글**: `useStrictHedge`

진입 전 pre-check (both):

```text
hedgeRatio = |longNotionalEst / shortNotionalEst|
hedgeRatio < 0.998 또는 hedgeRatio > 1.002 → 진입 거부
```

진입 후 트림:

- route: strict ON 시 `0.20%`, OFF 시 `2%`
- scheduler: pre-check는 strict 기준을 쓰지만, 진입 후 route와 동일한 0.20% strict trim으로 완전히 바뀐 것은 아님

즉, strict hedge는 **pre-check는 both에 적용**되지만,
**진입 후 미세 트림은 route 기준이 더 강하게 반영**되어 있다.

## 9. 부분구현 기능 상세

### 9.1 Drift Buffer [부분구현]

**토글**: `useDriftBuffer`  
**구현 위치**: `lib/opportunities.ts`  
**실행 경로 연결**: 없음

구현된 함수:

```typescript
calcDriftBuffer(displayedRate, recentRateHistory?, exchangeUsesInstantRate?)
```

동작:

- `recentRateHistory` 없음: 일반 거래소는 1bp, instantaneous rate 성격 거래소는 `max(1bp, |rate| × 5%)`
- `recentRateHistory` 있음: `max(|last1mChange|, |last5mChange| × 0.5, 1bp)`
- instantaneous rate 성격 거래소는 buffer에 `×1.5`

현재 상태:

- 함수는 존재
- 토글도 존재
- 하지만 scheduler의 실제 진입 EV 계산에는 아직 연결되지 않음

### 9.2 Conservative EV [부분구현]

**구현 위치**: `lib/opportunities.ts`  
**실행 경로 연결**: 없음

구현된 함수:

```typescript
calcConservativeEV(
  notionalUSD,
  shortRate,
  longRate,
  shortDrift,
  longDrift,
  roundTripFeePct,
  entryImpactPct,
  exitImpactPct,
)
```

반환 예시:

```typescript
{ expectedNetUSD, passesMinProfit, passesEVRatio, evRatio }
```

현재 상태:

- EV 계산 유틸은 존재
- 최소 수익 / EV ratio 판정 로직도 존재
- 그러나 실제 scheduler 진입 판단은 아직 기존 `calcNetSpreadPercent`, `calcHedgedNetSpreadPercent` 기반

### 9.3 Time-Normalized Scoring [부분구현]

**구현 위치**: `lib/opportunities.ts`  
**실행 경로 연결**: 없음

구현된 함수:

```typescript
calcTimeNormalizedScore(expectedNetUSD, capitalLockSec, fillProb?, fundingCaptureProb?)
```

개념:

```text
score = expectedNetUSD × fillProb × fundingCaptureProb / capitalLockSec
```

현재 상태:

- 함수는 존재
- 실제 opportunity ranking / scheduler selection에는 아직 미연결

## 10. 가드 체인 (실행 순서)

### 10.1 진입 전 가드

| 순서 | 가드 | 조건 | 적용 범위 | 비고 |
|------|------|------|-----------|------|
| 1 | Balance check | 잔고 >= margin + fee | both | 기존 로직 |
| 2a | Impact guard | `roundTripImpactBps > 12` | route만 | `useImpactGuards` ON 시 |
| 2a' | Slippage guard | `slippage > maxSlippagePercent` | scheduler + route(OFF 시) | legacy |
| 2b | Entry gap | `|entryGapPct| > threshold` | route만 | threshold source 변경 가능 |
| 2c | Profitability | `realNetSpread <= 0` | both | 기존 로직 |
| 3 | Hedge ratio | `ratio < 0.998 or > 1.002` | both | `useStrictHedge` ON 시 |
| 4 | Depth check | `targetNotional < $100` | scheduler만 | `useDynamicNotional` ON 시 |
| 5 | Timestamp check | `|shortFT - longFT| > 3s` | scheduler만 | `useConfirmedClose` ON 시 |

### 10.2 진입 후 가드

| 가드 | 조건 | 동작 | 적용 범위 |
|------|------|------|-----------|
| Hedge trim | strict ON: `> 0.20%`, legacy: `> 2%` | 초과분 부분 청산 | route 중심 |
| One-leg failure | 한쪽만 실패 | 성공 측 + partial rollback | both |
| Close retry | 청산 실패 | 30초 후 재시도 | scheduler |

| Bitget | 0.048% | 0.016% |
| Gate | 0.040% | 0.016% |
| BingX | 0.040% | 0.016% |

우선순위:

```text
feeOverrides[exchange] ?? EXCHANGE_FEES[exchange]
```

### 11.2 IOC-limit only 사용 시

- `useIocLimitOnly = true` → 진입 비용은 taker fee 기준
- cascade 모드 → maker / taker / mixed 가능

### 11.3 [미구현] 향후 작업

- `liveAccountFee` 실시간 조회
- `effectiveFee = liveAccountFee ?? feeOverride ?? preset` 적용
- 레퍼럴/리베이트를 Decision EV에서 제외하고 `realizedRebateUSD`로만 사후 집계
